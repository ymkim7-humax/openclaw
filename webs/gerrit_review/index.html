[ARHT-312] cwmp: InternetGatewayDevice.X_AIS_UplinkSetup
Commented
Project: airoha/2025q3 | Owner: [Marusys VINA] Jack
Feedback ### General Observations This is a significant feature addition for TR-069 Uplink management. While functional, there are several areas in the shell scripts and C code that could be hardened. ### 1. Shell Script: `X_AIS_UplinkSetup` * **Brittle Parsing:** In `get_X_AIS_UplinkSetup_UplinkStatus`, the use of `cut -d ' ' -f 2` on `/proc/xpon/ponInfo` output is sensitive to the number of spaces. If the driver output format changes slightly, this will break. Consider using `awk` or a more robust regex-based extraction. * **Quoting:** Several variables and command substitutions are unquoted. For example, `kill -USR1 $pid` should be `kill -USR1 "$pid"` and `$UCI_SET dualuplink.common.allow_admin=$new_value` should have quotes around the value to handle potential special characters or empty strings. ### 2. C Code: `blapi_traffic_cmd.c` * **Debug Print Clutter:** You added `printf("%s=%s, link_rate = %s\n", ...)` which seems intended for CLI output. Ensure this doesn't clutter system logs or interfere with other tools parsing the output of this command. ### 3. C Code: `dualuplink_set.c` * **Input Validation:** `set_mode` uses `atoi(value)` directly. If `value` is not a numeric string, `atoi` returns 0, which is a valid mode (PON-ETH). This might lead to unexpected behavior if junk data is passed via UBUS. Use `strtol` for better validation. * **Error Handling:** In `set_enable`, if `HalNetwork_getDualUplink` fails, the function returns -1 but doesn't log a specific reason other than a general error. Given this is a state-changing operation, more specific logging would help debugging field issues.
[HP2236BVA-134] Update ONT software version.
Commented
Project: airoha/2025q3 | Owner: [Marusys VINA] Karina
Feedback ### Potential Issues ### 1. Buffer Overflow / Truncation In `omci_get_sw_version`, `buffer` is 16 bytes and `sw_version` (the destination) is also 16 bytes. When you use `snprintf(sw_version, size, "HNI-%s", buffer)`, the prefix "HNI-" (4 bytes) plus the version string from the file will likely exceed 16 bytes. This will result in the version being truncated, possibly losing critical version info. ### 2. Performance: Excessive `system()` calls In `omci_image_read_state`, you are calling `system("uci set ...")` over 10 times in a row. Each `system()` call forks a shell, which is extremely heavy for an embedded system. * **Recommendation:** Use the `uci` C library directly (e.g., `uci_set`, `uci_commit`) which is already available in the environment, or concatenate the commands into a single shell script execution. ### 3. Logic: Default Version If `/etc/fw_info/version` is empty, `buffer[0]` will be `\0` and you default to `HNI-SW-V1.0`. However, if the file contains only a newline, `strcspn` will make it an empty string, which is handled, but it's worth verifying if this file is guaranteed to exist and have a specific format.

Commented

Feedback ### 1. Driver Performance & Safety (`sgpio-airoha.c`) * **Resource Management:** `airoha_sgpio_enable` and `airoha_sgpio_enable_rclk` perform `ioremap` and `iounmap` on every call. This is inefficient. These registers should be remapped once during probe. * **Busy Wait:** `airoha_sgpio_wait_for_shift` has a busy-wait loop `while (reg_val & BIT(31))`. This could hang the kernel if the hardware doesn't respond. Should have a timeout. ### 2. PWM Driver (`pwm-airoha.c`) * **Pin Range Validation:** Ensure `SGPIO_BASE + MAX_SGPIO_PINS` doesn't overlap with existing GPIO ranges or cause out-of-bounds access in arrays like `gen_wave_state`.
