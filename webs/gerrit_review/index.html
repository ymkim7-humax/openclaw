Click to see details ### 분석 개요 본 패치는 `HalMesh_getBackhaulCfg` 함수에서 유효하지 않은 Mesh Backhaul(BH) 마스크가 감지되었을 때 `HAL_FAILURE`를 반환하던 로직을 `HAL_SUCCESS`를 반환하도록 수정하여, GUI에서 발생하는 500 에러를 방지하고자 하는 목적을 가지고 있습니다. ### 상세 분석 1. **동작 변경 사항**: * 기존: `bh_mask`가 예상된 케이스(2.4G, 5G, Dual 등)에 해당하지 않을 경우 에러 로그를 남기고 즉시 `HAL_FAILURE`를 반환했습니다. * 변경: 동일한 상황에서 로그는 남기되, `break`를 통해 함수 끝으로 이동하여 `HAL_SUCCESS`를 반환합니다. 2. **잠재적 위험 요소**: * **초기값 의존성**: `stMeshCfg` 구조체가 함수 시작 부분에서 어떻게 초기화되는지가 중요합니다. 커밋 메시지에 따르면 "모든 인터페이스가 비활성화된 경우 기본 BH 인터페이스(5GHz)를 사용한다"고 되어 있으나, 코드상으로는 `default` 케이스에서 단순히 `break`만 수행할 뿐 `stMeshCfg`에 특정 값을 명시적으로 할당하는 로직이 보이지 않습니다. * 만약 이 함수 내부에서 `stMeshCfg`를 5GHz로 초기화한 뒤 `switch` 문에 진입한다면 의도대로 동작하겠지만, 그렇지 않다면 호출 측에서 초기화되지 않은 데이터를 읽게 될 위험이 있습니다. 3. **설계 의도**: * GUI 500 에러는 일반적으로 백엔드 API가 에러 코드(Non-zero)를 반환할 때 발생합니다. `HAL_SUCCESS`를 반환함으로써 상위 레이어에서 이를 정상으로 간주하게 하여 GUI 크래시를 막으려는 의도는 달성되나, 실제 설정값이 무엇으로 전달되는지 확인이 필요합니다. ### 권장 사항 * `default` 케이스에서 단순히 `break`를 하기보다는, 커밋 메시지의 의도대로 `stMeshCfg->backhaul = HAL_MESH_BH_5G;` (가칭)와 같이 명시적으로 기본값을 할당하는 것이 안전합니다. * 함수 시작 부분에서 `stMeshCfg`를 기본값으로 초기화하고 있는지 재확인하십시오. ### Verdict **Needs Improvement (Minor)** (GUI 에러를 막는 효과는 있으나, 명시적인 기본값 할당 로직이 추가되는 것이 코드 안정성 측면에서 바람직합니다.)

[HP2236BVA-155] Fix error cannot get IP Gateway address for all WAN Interface
Needs Revision
Project: airoha/2025q3 | Owner: [Marusys VINA] Dante
Click to see details ### Analysis The patch addresses the issue where the IP Gateway address cannot be retrieved for all WAN interfaces when HNI Port Binding is enabled. It achieves this by mirroring relevant routes (subnets and the primary default route) from interface-specific routing tables into the `RT_TABLE_MAIN` (main table). #### Key Improvements: 1. **State Tracking**: Introduced `installed_table` and `installed_main` flags in `struct device_route` to accurately track which tables a route has been applied to. This prevents orphaned routes or double-deletions during interface updates. 2. **Selective Mirroring**: Default routes are only mirrored to the main table if the interface is designated as the primary default WAN (`no_defaultroute` is false), preventing conflicting default gateways in the main table. 3. **Stability**: In `interface_update_proto_route`, route state is preserved during updates (via the `keep` flag), ensuring continuity during protocol events like DHCP renewals. 4. **Ubus Transparency**: Updated `ubus.c` to correctly filter and display routes based on their installation status in HNI configurations. #### Technical Observations: - **Mirroring Logic**: The use of `system_rt_main` to create a copy of the route with `rt_main.table = RT_TABLE_MAIN` is a standard and safe way to interact with the netlink subsystem in `netifd`. - **Atomic Operations**: `system_add_rt_main` performs an explicit `RTM_DELROUTE` followed by `RTM_NEWROUTE`. While this is an "upsert" pattern, it ensures the main table stays synchronized even if the route parameters changed slightly. - **Safety Checks**: `should_process_custom_table` correctly avoids mirroring routes that are already intended for the main, local, or default tables. #### Minor Feedback: - **Indentation**: There are several instances of inconsistent indentation (mixed spaces and tabs) in the patch file. For example, lines like `+ system_del_rt_main(dev, r);` appear to have spaces where tabs are expected by the `netifd` coding style. - **Error Handling**: The return value of the initial `system_rt_main(dev, route, RTM_DELROUTE)` in `system_add_rt_main` is ignored. This is generally acceptable as the delete will fail if the route doesn't exist, but it won't prevent the subsequent `NEWROUTE` from attempting to install it. ### Verdict The patch is logically sound and correctly implements the required routing behavior to fix gateway detection issues while maintaining system stability.
[ARHT-390] fix potential invalid memory access in DNS recap handling
Needs Revision
Project: airoha/2025q3 | Owner: Sungwook Joe(조성욱)
Click to see details ### 1. Critical Build Failure: Missing `mac_answer` The patch removes the definition of the global `mac_answer` array but continues to use it in `br_dns_packet_recap`. - **Removed:** `unsigned char mac_answer[ETH_ALEN] = { 0x02, 0xAA, 0xBB, 0x01, 0x23, 0x45};` - **Used:** `memcpy(eth_hdr(skb)->h_source, mac_answer, ETH_ALEN);` This will result in a compilation error: `'mac_answer' undeclared`. ### 2. Security: Out-of-Bounds (OOB) Read in DNS Parsing In `is_not_allowed_dns_query`, the code calculates `len` from the UDP header length and then uses it to access `skb->data` without verifying the actual packet size: ```c len = ntohs(udph->len) - sizeof(struct udphdr) - sizeof(dnsheader_t) - 4; ... body = skb->data + offset + sizeof(dnsheader_t); type = get_domain_name(body, len, domain, sizeof(domain)); ``` A malicious packet can provide a `udph->len` that is significantly larger than the actual data stored in the `skb`. While `skb_linearize()` ensures the data is contiguous, it does not guarantee that the buffer is as large as the UDP length field claims. This leads to an OOB read in `get_domain_name`. ### 3. Invalid Memory Access: Fragile MAC Header Check The check for the existence of an Ethernet header is manually implemented and potentially dangerous: ```c eh = eth_hdr(skb); if ((dns_ver == DNS_V4 && ((unsigned char *)iph - (unsigned char *)eh >= ETH_HLEN)) ... ``` If `skb->mac_header` is not set (e.g., in certain tunnel or ppp scenarios), `eth_hdr(skb)` may return an invalid pointer (e.g., `skb->head + 0xFFFF`). Relying on pointer arithmetic between potentially unrelated memory addresses is unsafe. - **Recommendation:** Use `skb_mac_header_was_set(skb)` to verify the MAC header's validity. ### 4. Performance: Invasive Hook in `__dev_queue_xmit` The patch adds a DNS query inspector and `skb_linearize()` call into the hot path of `__dev_queue_xmit`: ```c if (!is_recaped_dns_packet(skb) && is_not_allowed_dns_query(skb, NULL)) goto drop; ``` This performs deep packet inspection (DPI) and potentially expensive memory reallocation/copying (`skb_linearize`) for every DNS packet leaving the system. This should ideally be handled at the netfilter/iptables level or within specific bridge hooks rather than the generic device transmission path. ### 5. Code Quality & Logic - **Indentation:** The changes in `br_input.c` and `dnstrap.c` contain mixed tabs and spaces, violating kernel coding standards. - **Untrusted Input:** `ntohs(udph->len)` is used to calculate `len` without checking if it's smaller than the headers (`sizeof(udphdr) + sizeof(dnsheader_t) + 4`), which could lead to a negative value or underflow logic issues. ### 6. Correctness: Re-fetching Headers The patch correctly re-fetches `iph` and `udph` after `pskb_expand_head`, which is a good fix for the reported crash. However, the other issues mentioned above make the patch unsafe in its current form.
**Verdict:** **Needs Revision (Critical)** - The patch will fail to compile and contains a potential out-of-bounds read vulnerability.
[HP2236BVA-44] Fix cannot access WEBUI from WAN side when disable block service control
Needs Revision
Project: airoha/2025q3 | Owner: [Marusys VINA] Vincent
저는 전문가로서 해당 패치를 분석한 결과, 보안 및 로직 측면에서 심각한 부작용을 초래할 수 있는 코드로 판단됩니다.
Click to see details ### 분석 내용 1. **비논리적인 규칙 반전 (Logic Inversion)** * 기존 코드: `rulePolicy = (!strcmp(rule.action, ATTR_BLOCK)) ? "-j DROP" : "-j ACCEPT";` * 규칙의 설정에 따라 BLOCK이면 DROP, 아니면 ACCEPT를 적용합니다. * 변경 코드: `rulePolicy = (!strcmp(rule.action, ATTR_BLOCK) == rule.active) ? "-j DROP" : "-j ACCEPT";` * 이 수식은 `rule.active`가 `false`(0)일 때 동작을 완전히 반전시킵니다. * **문제점:** 만약 어떤 규칙이 `ALLOW`(`ACCEPT`) 규칙인데 비활성화(`active=false`)된 경우, `(0 == 0)`이 되어 `-j DROP`이 적용됩니다. 즉, **특정 접근을 허용하려다 규칙을 끈 것이 오히려 명시적인 차단 규칙으로 변하게 됩니다.** 이는 사용자 의도와 완전히 상반되는 보안 위협이 될 수 있습니다. 2. **비활성 규칙의 강제 적용** * 변경 전에는 `rule.active != true`이면 `continue`를 통해 규칙을 건너뛰었습니다. * 변경 후에는 `serviceName`이 "Whitelist"가 아닌 모든 비활성 규칙을 강제로 프로세스에 포함시킵니다. * 이로 인해 시스템의 모든 비활성화된 Access Control 규칙들이 위의 반전된 로직에 따라 예상치 못한 `DROP` 또는 `ACCEPT` 규칙으로 변하여 방화벽(iptables 등)에 삽입됩니다. 3. **부작용 (Side Effects)** * WEBUI WAN 접근 문제는 해결될지 모르나(비활성화된 BLOCK 규칙이 ACCEPT로 변하므로), 시스템에 설정된 다른 모든 `Allow` 규칙들이 비활성화 상태일 때 `Block` 규칙으로 돌변하여 정상적인 트래픽을 차단하게 됩니다. * 이는 매우 위험한 접근 방식이며, 특정 서비스("Whitelist"가 아닌 경우)에만 이 로직을 적용하는 것조차 일반적인 보안 엔진 설계 원칙(비활성 규칙은 무시됨)에 어긋납니다. ### 권장 사항 * 비활성화 시 특정 접근을 허용해야 한다면, 비활성화된 규칙을 강제로 반전시켜 적용하는 것이 아니라 기본 정책(Default Policy)을 확인하거나, 해당 서비스가 비활성화될 때 명시적인 ALLOW 규칙이 추가되도록 설계를 변경해야 합니다. * 현재의 패치는 "규칙을 끄면 동작이 반대(Allow <-> Block)가 된다"는 위험한 가정을 전제로 하고 있습니다. ### Verdict **CRITICAL / BUGGY** - 비활성화된 허용 규칙이 차단 규칙으로 변하는 치명적인 로직 오류를 포함하고 있습니다.
